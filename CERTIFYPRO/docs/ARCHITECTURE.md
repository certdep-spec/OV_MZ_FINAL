# CertifyPro v3.0: Архитектурный Дизайн (For Developers)

**Версия:** 3.0
**Цель документа:** Детальное описание архитектурных паттернов, слоев и принципов взаимодействия компонентов для новых разработчиков.

---

## 🏗️ Обзор Архитектуры

CertifyPro v3.0 спроектирован по принципам **Чистой Архитектуры (Clean Architecture)** с явным разделением ответственности между UI, Сервисами Бизнес-Логики и Уровнем Доступа к Данным (DAL). Система построена вокруг паттерна **Dependency Injection (DI)** для обеспечения тестируемости.

## 🧩 Слои Приложения (Layers)

### 1. Presentation Layer (GUI)
*   **Технология:** CustomTkinter.
*   **Ответственность:** Обработка пользовательского ввода, отображение данных и вызов сервисных методов.
*   **Принцип:** Этот слой не должен содержать бизнес-логику. Он взаимодействует только с **Service Layer** через интерфейсы (абстракции).

### 2. Service Layer (Business Logic)
*   **Ядро Системы.** Содержит всю основную бизнес-логику и оркестровку процессов.
*   **Компоненты:**
    *   `ClientManager`: Центральный компонент, отвечающий за инициализацию, переключение контекста и управление жизненным циклом клиента (загрузка конфигурации, проверка доступности DB).
    *   `DocumentGeneratorService`: Оркестрирует процесс генерации документов. 

### 3. Configuration & Context Layer
*   **Компонент:** `ClientConfig` (используя Python `dataclasses` модуля `client_manager`).
*   **Ответственность:** Инкапсуляция всех настроек, специфичных для одного клиента.
*   **Механизм:** Конфигурация жестко валидируется при загрузке из `profiles.yaml`. Это гарантирует, что все сервисы работают только с проверенными и типизированными данными. Глобальное состояние инкапсулировано через `get_client_config()`.

### 4. Document Generation Layer (Strategy Pattern)
*   **База:** `BasePartyDocumentGenerator` (Абстрактный базовый класс).
*   **Паттерн:** **Strategy**. Каждый конкретный генератор наследуется от базы и реализует метод `generate()`.
*   **Динамика:** Структурированный процесс генерации выбирается на основе суффикса, указанного в активной конфигурации клиента, через `TemplateResolver`.

### 5. Data Access Layer (DAL)
*   **Технология:** SQLite3 (через инструменты баз данных приложения).
*   **Ответственность:** Абстрагирование всех операций с данными (чтение из DB, запись логов, получение шаблонов).
*   **Принцип:** Сервисы всегда должны взаимодействовать с модулем базы данных.

## 🔄 Поток Данных и Взаимодействие (Flow Example: Document Generation)

1.  **GUI** запрашивает генерацию документа (клик кнопки).
2.  **Service Layer** получает запрос, обращается к **`ClientManager`**, который предоставляет активный объект **`ClientConfig`**.
3.  Соответствующий генератор (например, `UgodaGenerator`) извлекает `template_suffix` и работает по своему алгоритму замены паттернов.
4.  Стратегия использует DAL для загрузки исходного шаблона DOCX и подставляет данные из SQLite (через `DatabaseManager`), выполняя замену полей `{{PATTERN}}`.
5.  Результат возвращается в форму документа (сохраненный `.docx`).

## 💡 Ключевые Паттерны Использования

*   **Strategy:** Для реализации вариативности генераторов документов (адаптация к суффиксам разных клиентов при подгрузке шаблонов).
*   **Dependency Injection:** Сервисы могут и должны принимать свои зависимости через контейнер `di.py`, что позволяет легко подменять реальные реализации при тестировании.

## 🔧 Автоматическая инициализация клиентов (Auto-Provisioning)

**Добавлено в v3.1.0:** При добавлении нового клиента через GUI лаунчера инфраструктура создаётся автоматически — без ручного редактирования `profiles.yaml` или копирования файлов.

### Компоненты

*   **`client_provisioner.py`** (в `client_launcher/`): Главный модуль авто-создания. Выполняет:
    1.  Создание структуры папок: `<papka_proektu>/data/`, `<papka_proektu>/data/Documents/`
    2.  Инициализацию пустой БД `certify.db` из единой SQL-схемы (`db_schema.sql`)
    3.  Регистрацию клиента в `profiles.yaml` (атомарная записи через временный файл)
    4.  Откат при ошибке (удаление записи из `applicants.db`)

*   **`db_schema.sql`** (в `CERTIFYPRO/core/database/`): Единый источник истины для схемы БД. Заменяет дублирование между `di.py` и `db_manager.py`. Содержит CREATE TABLE для 6 таблиц: `products`, `standards`, `applications`, `parties`, `ingredients`, `production_facilities`.

### Поток данных при создании клиента

```
GUI: "Керувати заявниками" → "Додати"
    ↓
applicants_db.add_applicant(applicant, auto_provision=True)
    ↓ INSERT в applicants.db
    ↓
client_provisioner.provision_new_client()
    ├── 📁 mkdir data/<papka_proektu>/data/
    ├── 📁 mkdir data/<papka_proektu>/data/Documents/
    ├── 💾 CREATE TABLE из db_schema.sql
    └── 📝 profiles.yaml: добавлена запись клиента
    ↓
Если ошибка → DELETE из applicants.db (откат)
```

### Fallback: динамические клиенты

Если клиент запущен напрямую (не через лаунчер) и отсутствует в `profiles.yaml`, `config.py` создаёт минимальную инфраструктуру на лету: папки + пустая БД. Это обеспечивает работоспособность даже при «ручном» запуске.

### Транслитерация

`papka_proektu` на кириллице (например, "НОВИЙ_КЛІЄНТ") транслитерируется в `client_id` латиницей ("NOVYJ_KLIENT") для использования в `profiles.yaml` и внутренних путях.
